# 设备消息数据存储设计

> 设备消息持久化设计：属性上报 / 事件上报 / 消息日志（全部设备消息的上下行）统一按产品存储策略路由（TDengine 无模式写入）；设备属性查询与设备日志查询接入该存储。

## 1. 背景与目标

平台此前设备上报属性、上报事件、命令上下发均无持久化。本设计建立设备消息数据存储体系（落库 + 历史查询），并将既有设备属性查询与设备日志查询接入该存储：

- **三类消息**：属性上报、事件上报、消息日志（全部设备消息的上下行 —— 命令上下发、回复、注册/注销/上下线等连接生命周期消息）
- **三类消息统一按产品存储策略路由**，存储策略可插拔、将来绑定到产品配置（当前 `DeviceProductOperator.getStoragePolicy()` 写死）：
  - `tdengine-row`（TDengine 行布局：一条消息一行、属性摊平为列）—— 默认策略
  - `tdengine-column`（TDengine 单值列布局：属性表每属性一行 + 固定类型值列）
- **事件上报按原始消息存储，不等同告警日志**：告警规则引擎后续实现，规则触发后再写告警日志（不在本方案范围）
- 三个监听器（消费消息、转换业务模型并落库）、三个数据服务（面向上层业务的落库与查询）

### 2.2 数据流

```
上行（属性上报 / 事件上报 / 全部消息）：
设备 → MQTT → DefaultDecodedClientMessageHandler.handle ② → eventBus.publishAsync(消息)
    → sa-admin 监听器（消息 → 业务模型，回填设备上下文）→ 数据服务 store
    → device.getStorageStrategy()（经产品存储策略 ID 路由）→ 策略 save → TDengine

下行（命令）：
DeviceSendOperator → LocalDeviceMessageSender.doSend 发送成功 → eventBus.publishAsync(填充后消息)
    → MessageLogStorageListener → 同上策略路由（direction=down）
设备回复经上行路径再入库（direction=up，同 messageId 独立一行）
```

### 2.3 关键机制

- **@EventListener 监听（经事件总线桥接）**：`SpringEventBus.publish` 将事件同时转发给 Spring 的 `ApplicationEventPublisher`（SpringEventBus.java L74-76），故三个监听器用 Spring `@EventListener` 直接收到 `eventBus.publish/publishAsync` 发布的事件，**上行/下行发布点均无需改动**。匹配语义：方法参数为父类即收到全部子类事件（`AbstractDeviceMessage` 覆盖全部设备消息，含 ChildDeviceMessage/ChildDeviceMessageReply）；泛型经 `ResolvableTypeProvider` 精确匹配 —— `ChildDeviceMessage<T>`/`ChildDeviceMessageReply<T>` 实现该接口，监听方法直接声明具体内层泛型（如 `ChildDeviceMessage<ReportPropertyMessage>`）即只收该内层类型的子设备消息，无需 instanceof 守卫（项目既有 `CrudEvent<T>` 同款用法）
- **@EventListener 的线程语义**：`publishAsync` 在线程池上执行 `publish`，Spring 广播器随后在**该异步线程**上同步调用 @EventListener 监听器 —— 监听器天然异步、无需 `@Async`，也不阻塞消息处理线程；上行与下行两处发布点均为 publishAsync
- **下行发布点**：`LocalDeviceMessageSender.doSend` 是单机 + 集群（远端转发最终落在设备所在节点 localSender）唯一实际发送点，发布恰好一次；发送**成功后**才发布（失败命令未到达设备，不入库）
- **注册器恒装配 + 空策略兜底**：`StorageAutoConfiguration` 无条件装配注册器，注册器恒持有 `EmptyStorageStrategy`、`get()` 永不返回 null —— 存储总开关（`iot.storage.enabled=false`，默认）只决定策略 bean 是否装配；未开启/无匹配策略时经注册器落到空策略：写入告警一次不阻断消息流、查询明确抛错。策略经设备操作对象解析（`DeviceOperator.getStorageStrategy()`，设备未绑定产品/产品不存在同样兜底空策略），监听器/数据服务不做判空，无 TDengine 环境照常启动

## 3. 存储策略体系（sa-base）

### 3.1 策略 ID

```java
public final class StoragePolicy {
    /** TDengine 行存储（多列）：属性一条消息一行、属性摊平为列；事件/日志一行一条消息 */
    public static final String TDENGINE_ROW = "tdengine-row";
    /** TDengine 单值列存储：属性表每属性一行（tags={device_id, property} + 固定类型值列），事件/日志表与 row 同形态 */
    public static final String TDENGINE_COLUMN = "tdengine-column";
    // 将来: INFLUXDB / CLICKHOUSE / ELASTICSEARCH ...
}
```

### 3.2 StorageStrategy 接口（以业务模型为契约）

```java
public interface StorageStrategy {

    /** 策略 ID — 与 StoragePolicy 常量对应（注册器按此收集/查找，产品经存储策略 ID 路由到本策略） */
    String getId();

    /** 消息落库 — 三类业务数据的唯一写入口：入参为抽象父类型 StorageData，策略按实际子类分派 */
    void save(StorageData data);

    /** 属性历史分页查询 — 查指定属性（property 必填）历史上报值，时间倒序；总数与当前页一次返回 */
    PageResult<PropertyData> queryPropertyHistory(PropertyHistoryQuery query);

    /** 批量查询属性最新上报值 — 每属性独立取最后一条非空记录；结果键 = 属性 id、有序；无记录属性不返回 */
    Map<String, LatestPropertyValue> queryLatestPropertyValues(LatestPropertyQuery query);

    /** 事件历史分页查询 — 时间倒序；总数与当前页一次返回 */
    PageResult<EventData> queryEventHistory(EventHistoryQuery query);

    /** 消息日志分页查询 — 时间倒序；总数与当前页一次返回 */
    PageResult<MessageLogData> queryCommandLogHistory(CommandLogQuery query);
}
```

**设计决策**：

- **策略即领域服务**：落库/查询的语义（消息模型 ↔ 行形态编解码、建表布局、查询方言）全部收敛在策略内部 —— 上层不感知具体存储库，也不构造任何 SQL / 行数据；查询只传业务条件（productId 需先经设备上下文解析，见 §8），结果直接返回业务模型
- **写入口唯一**：`save(StorageData)` 以抽象父类为入参，策略按实际子类分派到属性/事件/日志落库；缺设备/产品维度或未知类型仅记日志跳过，不阻断消息流
- **实现策略可分层**：时序策略族按「布局差异 × 后端方言」两轴抽分为抽象基类 + 叶子（见 §5），非时序库（ES 等）可直接扁平实现本接口
- **同步接口**：save/query 均为同步方法（内部阻塞 JDBC）；监听器在事件总线异步派发线程中调用，MVC 服务直接调用取结果
- **分页收敛在策略**：count + 数据两查收敛在策略内一次返回 `PageResult`，不做 limit/offset 外泄

### 3.3 StorageStrategyRegistry 注册器（恒装配 + EmptyStorageStrategy 兜底）

```java
public class StorageStrategyRegistry {

    private final Map<String, StorageStrategy> strategyMap = new ConcurrentHashMap<>();

    /** 兜底空策略 — 恒持有：get() 未命中时返回（写入告警一次、查询抛 BusinessException） */
    private final StorageStrategy emptyStrategy = new EmptyStorageStrategy();

    /** Spring 收集全部策略 bean 注册；ID 为 null 跳过并告警；重复 ID 告警后者覆盖；注册表为空时 info 日志一次 */
    public StorageStrategyRegistry(List<StorageStrategy> strategyList) { ... }

    /** 按策略 ID 查找 — 永不返回 null：id 为 null / 未注册（含存储未开启的全局空表）返回 EmptyStorageStrategy */
    public StorageStrategy get(String id) { ... }
}
```

- **无条件装配**：`StorageAutoConfiguration` 恒装配注册器（无任何 @ConditionalOnProperty）—— `iot.storage.enabled` 总开关只决定策略 bean 是否装配（见 §11.2），注册器 + EmptyStorageStrategy 始终存在，监听器/数据服务直接使用、不做判空
- **空列表场景**：Spring 对 `List<StorageStrategy>` 注入的是**空列表而非 null**（如 tdengine 未启用且无其他策略）—— 注册表为空但 `get()` 仍返回 EmptyStorageStrategy，不 NPE。不为此加 `@ConditionalOnBean`（组件扫描下 bean 注册顺序不可靠）
- **EmptyStorageStrategy 语义**（`get()` 未命中时的默认行为）：写入路径（save）进程级告警**一次**后静默 —— 存储默认关闭是常态，不刷屏、不阻断消息流；读路径（四个查询方法）抛 `BusinessException("设备消息数据存储未开启或无匹配存储策略，无法查询历史数据")` —— 历史数据查询需要真实存储，不做静默空结果
- **策略解析链**（`DefaultDeviceOperator.getStorageStrategy()`）：`getProduct().map(product -> registry.get(product.getStoragePolicy())).defaultIfEmpty(new EmptyStorageStrategy())` —— 设备未绑定产品/产品不存在同样兜底空策略，**Mono 恒非空**，数据服务 block 后恒有策略可用

将来新增 InfluxDB / ClickHouse 策略只需实现 `StorageStrategy` 并声明为 bean，零改动自动注册。

## 4. 数据模型（sa-base `storage.model`）

### 4.1 业务模型（抽象父 + 三子类）

```java
public abstract class StorageData {   // 三类消息公共字段（全字段由监听器转换时一次填齐，策略层不触碰设备上下文）
    private String deviceId;     // 设备 id（tag，区分产品下设备）
    private String productId;    // 产品 id（决定表名 device_xxx_{productId}，监听器回填）
    private String deviceName;   // 设备名称（冗余字段，取设备自配置 DeviceField.DEVICE_NAME 快照，便于展示）
    private String messageId;    // 消息 id
    private long timestamp;      // 消息时间（毫秒，落 ts 主时间列与 create_time 冗余列）
}

public class PropertyData extends StorageData {   // 属性上报：一条消息一个对象
    private Map<String, Object> properties;       // 属性 Map 业务原样传入；行布局由策略决定（row 摊平 / column 每属性一行）
}

public class EventData extends StorageData {      // 事件上报（原始消息存储，不等同告警日志）
    private String event;        // 事件标识（id，tag）
    private String type;         // 事件类型 info/warning/error（列，取物模型 EventMetadata.getType()）
    private String dataType;     // 事件数据的物模型数据类型名（tag，取物模型 valueType 的 type 名）
    private String data;         // 事件数据 JSON 字符串（紧凑序列化；数据类型由物模型动态定义，统一 JSON 存储）
}

public class MessageLogData extends StorageData { // 消息日志：平台下发与设备上报双向，一条消息一个对象
    public static final String DIRECTION_UP = "up";     // 设备上报（回复）
    public static final String DIRECTION_DOWN = "down"; // 平台下发
    private String direction;      // up=设备上报（回复）/ down=平台下发
    private String commandType;    // = TopicMessageCodec 枚举名（readProperty/writeProperty/functionInvoke/disconnect…，回复追加 Reply 后缀）
    private String content;        // 消息内容 JSON 字符串（整条消息全量序列化，含 headers 不清空）
}
```

**时序库只追加绝不 UPDATE**：下发行与回复行各自独立（同 messageId 关联），执行结果（success/code/message）含在回复行 content JSON 内，不单独落列。

### 4.2 查询条件对象（业务条件，不含任何 SQL）

| 对象 | 字段 | 说明 |
|---|---|---|
| `PropertyHistoryQuery` | productId / deviceId / property / startTime / endTime / pageNum / pageSize | property 必填（历史查询按单个属性分页）；时间毫秒含边界、可空 |
| `EventHistoryQuery` | productId / deviceId / event / startTime / endTime / pageNum / pageSize | event 可空 = 全部事件 |
| `CommandLogQuery` | productId / deviceId / commandTypes / direction / deviceName / startTime / endTime / pageNum / pageSize | commandTypes 为 TopicMessageCodec 枚举名集合（tag IN，多选直传）；direction/deviceName 字段列等值；三者可空 = 不按该条件过滤 |
| `LatestPropertyQuery` | productId / deviceId / propertyIds | 待查属性 id 集合（空集合 = 无查询，返回空结果） |
| `LatestPropertyValue` | value / timestamp | 单个属性最新上报值：列值原样（数值/布尔/文本，对象为 JSON 字符串）+ 上报时间毫秒 |
| `TimeseriesRow` | —（查询行包装） | getString/getLong/get/asMap；行键即写侧列名（下划线小写一套命名），动态属性列名经 `TimeseriesLayout#rowKey` 归一化 |

查询排序固定**时间倒序**（消息数据均按时间展示）。

### 4.3 逻辑列约定（命名单一来源见 §5.2）

| 数据类 | 表（= 前缀 + productId） | tags（等值过滤列） | 固定字段列 | 动态列 |
|---|---|---|---|---|
| 属性（row 布局） | `device_properties_{productId}` | `device_id` | `message_id`, `create_time`, `device_name` | 各属性名:值（一条消息一行，属性摊平为列） |
| 属性（column 布局） | `device_properties_{productId}` | `device_id`, `property` | `message_id`, `create_time`, `device_name` | 单值类型列其一：`long_value`/`double_value`/`boolean_value`/`date_value`/`string_value` |
| 事件 | `device_events_{productId}` | `device_id`, `event`, `data_type`（缺失不落） | `message_id`, `create_time`, `device_name`, `type`, `data` | — |
| 消息日志 | `device_message_logs_{productId}` | `device_id`, `command_type` | `message_id`, `create_time`, `device_name`, `direction`, `content` | — |

- **表按产品隔离**（表数 = 产品数），`device_id` 作 tag 区分设备并支持产品维度等值过滤；三表由 schemaless 按 tag 自动创建超级表与子表（每设备一张子表）
- **主时间列 `ts`**：TDengine 主键列，行协议尾部时间戳落此列，查询恒按 ts 倒序
- **保留列名**：属性名不得占用 `message_id`/`create_time`/`device_name`（否则摊平列会覆盖保留列）—— 由产品物模型校验上游兜底，策略写入再兜一层（`SmartPoint.Builder#fields` 批量灌入时自动跳过保留列名）
- **create_time** = 消息时间戳（BIGINT 毫秒，与 ts 同值，作普通列便于业务查询/展示）；`device_name` 为写入时设备名称快照（设备改名只影响后续行）

## 5. 时序策略族（sa-base `storage.timeseries`）

### 5.1 三级抽象（布局差异 × 后端方言两轴正交）

```
TimeseriesStorageStrategy（抽象基类）
    ├── 事件表 / 消息日志表：行与单值列两种布局形态完全一致（固定字段、无动态列）
    │     → 写入行协议、条件分页 SQL、查询行解码与 PageResult 组装在本类一次实现
    ├── 属性表：布局差异所在（动态摊平列 vs 每属性一行单值列）
    │     → saveProperty / queryPropertyHistory / queryLatestPropertyValues 留为抽象方法
    └── 具体库方言（建库 / 物理写入 / 查询执行）经 TimeseriesChannel 注入，
          叶子策略（TdengineRowStrategy / TdengineColumnStrategy）只做构造注入与策略 ID 声明
```

- `save(StorageData)` 在基类为 `final`：按住处维度校验（设备/产品缺失跳过）后按实际子类分派到 `saveProperty`/`saveEvent`/`saveMessageLog`
- 分页两查（count + 数据）与分页结果组装（页码/页大小由查询对象的 limit/offset 反推）在基类一次实现，事件/日志/属性历史共用；总数 0（含表不存在）或 limit<=0 短路不查数据

### 5.2 TimeseriesLayout — 命名方案单一来源

表名/tag/列名约定与值落列分派集中于此，供行/列布局策略与行协议构建共享，避免字面量散落漂移；将来接入新时序库沿用同一命名，产品切换存储策略不破坏历史查询语义：

- **表前缀**：`device_properties_` / `device_events_` / `device_message_logs_`
- **tag 键**：`device_id`、`property`（column 属性行）、`event`、`data_type`、`command_type`
- **逻辑保留列**：`message_id`、`create_time`、`device_name`
- **主时间列**：`ts`
- **事件/日志固定列**：`type`、`data`（事件）；`direction`、`content`（日志）
- **column 单值类型列**：`long_value`（BIGINT）/ `double_value`（DOUBLE）/ `boolean_value` / `date_value`（毫秒）/ `string_value`（字符串或紧凑 JSON），`COLUMN_VALUE_KEYS` 定扫描序
- **工具方法**：`rowKey(columnName)`（驼峰转下划线小写，动态属性列查询键归一化，写读同一套命名）、`isReservedField(property)`、`valueColumnName(value)`（Java 值 → 单值列名，与行协议类型分派对齐）

### 5.3 TimeseriesQuery — 查询 SQL 构建器（时序家族查询方言统一出口）

条件链式追加（空值判空内敛于各方法，调用方无需外在判空）：

```java
TimeseriesQuery.from(table)
    .eq(TAG_DEVICE_ID, deviceId)         // 列等值（空白值跳过），单引号翻倍转义
    .fromTime(startTime).toTime(endTime) // ts 毫秒范围（含边界，null 跳过）
    .eq(FIELD_DIRECTION, direction)      // 字段列等值
    .in(TAG_COMMAND_TYPE, commandTypes)  // 列集合包含（空集合/null 跳过）—— 类型多选直传
    .limit(pageSize).offset((long) (pageNum - 1) * pageSize);
```

- 三种出参：`pageSql()`（SELECT * + 条件 + ts 倒序 + LIMIT/OFFSET）、`countSql()`（`COUNT(*) AS total`，别名常量 `COUNT_ALIAS`）、`firstSql()`（链式 `columns(...)` + 恒追加 ts + 排序 + LIMIT 1，最新值查询用）
- 条件以追加序 AND 连接、空条件组不渲染 WHERE 段；`isNotNull(column)` 用于动态属性列收窄（row 布局属性历史 / 最新值定位）
- 三形态输出与查询解码约定逐字节稳定，策略测试据此做精确 SQL 断言

### 5.4 SmartPoint — 业务侧行协议点（写路径）

builder 模式构造（`table` / `timestamp` / `tag` / `field` / `fields` 批量灌入），`toLineProtocol()` 内部借 InfluxDB `Point` 序列化为行协议字符串（键排序、转义与类型后缀由库处理，不手写拼接）：

- `sanitizeMeasurement(table)`：表名非字母数字下划线替换为 `_`，数字开头加 `d_` 前缀（TDengine 表名约束）
- `column(Object)`：Java 值类型分派（整数→long、浮点→double、Boolean 原样、Date→毫秒 long、字符→toString、集合/Map/其他对象→Jackson 紧凑 JSON）
- `Builder.fields(Map)`：面向属性动态列整批灌入，键/值 null 与**保留列名自动跳过**（属性不得覆盖消息元数据列；元数据一律经显式 `field()` 添加）
- tags 由 Point 输出不带引号（InfluxDB 风格），TDengine schemaless 按位置解析 tag 一律落 NCHAR 字符串，数值形态 tag 值（如 deviceId）无类型歧义

### 5.5 字段值 → 行协议类型映射（通用）

行内**每个字段**的值按 Java 类型落列（属性摊平后属性名即列名，schemaless 自动建列；事件/日志的固定列同样适用）：

| Java 值类型 | 落列类型 | 示例（Point 实际输出） |
|---|---|---|
| 整数（byte/short/int/long/BigInteger） | BIGINT | `count=25i` |
| 浮点（float/double/BigDecimal） | DOUBLE | `temperature=25.6` |
| Boolean | BOOL（原生布尔） | `online=true` |
| String/enum | NCHAR 引号串 | `status="on"` |
| List/数组 | NCHAR（紧凑 JSON 字符串） | `list="[1,2]"` |
| Map/对象 | NCHAR（紧凑 JSON 字符串） | `config="{\"a\":1}"` |
| Date/时间 | BIGINT（毫秒） | `time=1720000000000i` |

数值按种类分落 **BIGINT / DOUBLE**（与物模型数据类型 int/long/float/double 对齐）。**后缀**：整数/时间毫秒输出 `i` 后缀、浮点无后缀，TDengine schemaless 原生接受（按 BIGINT / DOUBLE 解析），转义由 `Point.toLineProtocol()` 统一处理。

**类型冲突**：同一列跨消息类型或数值种类变化（如某属性 int → float、数值 → 字符串）会导致 schemaless 该批写入失败 —— 仅记日志不阻断消息流；产品物模型校验在上游兜底（属性类型稳定）。

**行协议示例**（measurement 为 `device_*_{productId}`，示例产品 100、设备 10001；`create_time` 按 Date/时间规则落 BIGINT 毫秒）：

```
device_properties_100,device_id=10001 message_id="m1",create_time=1720000000000i,device_name="温控器01",temperature=25.6,status="on" 1720000000000
device_events_100,device_id=10001,event=temp_alarm,data_type=object message_id="m1",create_time=1720000000000i,type="warning",device_name="温控器01",data="{\"temp\":68}" 1720000000000
device_message_logs_100,device_id=10001,command_type=writeProperty direction="down",message_id="m1",create_time=1720000000000i,device_name="温控器01",content="{\"properties\":{}}" 1720000000000
device_message_logs_100,device_id=10001,command_type=writePropertyReply direction="up",message_id="m1",create_time=1720000000123i,device_name="温控器01",content="{\"success\":true,\"properties\":{}}" 1720000000123
```

**已知偏差**（schemaless 无手工 DDL 的必然结果，与《IoT平台详细设计文档》1.9 的差异）：布尔值为原生 BOOL 列、时间值落 BIGINT 毫秒列，而非 TIMESTAMP 列；`templateId` tag 暂不落（产品配置绑定存储策略时再补）。

### 5.6 TimeseriesRow — 查询行读取器

通道查询返回行（Map）的包装：`getString`/`getLong`/`get`/`asMap` 取值转换内聚一处，解码处不再出现裸 get 与散落的类型转换；行键即写侧列名（`TimeseriesLayout` 常量），动态属性列名由调用方经 `rowKey` 归一化后传入。

### 5.7 两种布局的差异（仅属性表三处）

| 环节 | row 布局（tdengine-row） | column 布局（tdengine-column） |
|---|---|---|
| 写入 | tags={device_id}；fields = 保留列 ∪ 属性摊平列（属性集整批灌入，保留列名/null 自动防护） | 一条上报消息的属性拆为多行（tags={device_id, property}，行间共享保留列按 messageId 关联还原一次上报）；值落单值类型列其一 |
| 属性历史 | 属性为动态列 → `{property} IS NOT NULL` 收窄行集后 count + 时间倒序分页（一行 = 一次上报，整行解码） | `property` 为 tag 等值条件进 SQL 收窄（一行 = 一个属性值） |
| 最新值 | 每属性独立取该属性列 ts 倒序首行 | 值列类型未知 → 5 类型值列 + ts 全取最后一行，取首个非空值列即属性值（`COLUMN_VALUE_KEYS` 扫描序） |

事件/消息日志两表在两种布局下形态一致（固定字段、无动态列），读写由基类一次实现；row 布局查询行解码时属性 = 除保留键（device_id/message_id/create_time/device_name）与主时间列 ts 外的其余列。

## 6. TDengine 实现（sa-base `storage.tdengine`）

### 6.1 依赖与连接

- 依赖：`com.taosdata.jdbc:taos-jdbcdriver` **3.2.7**（根 pom dependencyManagement 管版本，sa-base pom 引用；Java 8 编译）
- 行协议构建依赖：`com.influxdb:influxdb-client-core` **6.12.0**（仅借其 `Point` 对象 → 行协议字符串的序列化能力，不引其 HTTP 写入客户端；Java 8 兼容；TDengine 驱动自身无此类对象，schemaless 只收字符串行协议）
- 驱动：默认 **`com.taosdata.jdbc.TSDBDriver`**（`jdbc:TAOS://host:6030`，原生 JNI；**3.2.7 无 `TaosDriver` 类**）；备选 `com.taosdata.jdbc.rs.RestfulDriver`（`jdbc:TAOS-RS://host:6041`，纯 Java）—— `TdengineProperties.getJdbcUrl()` 按 driver-class-name 自动推导 url
- 连接池：独立 `DruidDataSource`（非 @Primary，不干扰 MySQL 主数据源）；**`initial-size=0, min-idle=0` 惰性建连** —— TDengine 未启动时应用照常启动，写入失败仅告警；校验语句 `SELECT SERVER_VERSION()`
- 连接串不带库名（库可能尚不存在）；写入由 `SchemalessWriter` **构造器绑定目标库**（带库名的 6 参 write 重载在 3.2.7 已废弃）

### 6.2 自动建库（TdengineChannel#initStorage，@PostConstruct）

```sql
CREATE DATABASE IF NOT EXISTS {database} PRECISION 'ms' KEEP {keep} DURATION {days}
```

失败仅 `log.warn` 不抛（TDengine 未启动/无权限时应用照常启动，写入时再暴露）；`PRECISION 'ms'` 与消息时间戳（毫秒）及 `SchemalessTimestampType.MILLI_SECONDS` 三方对齐。

### 6.3 行协议写入（writeLines）

```java
try (Connection connection = dataSource.getConnection();
     SchemalessWriter writer = new SchemalessWriter(nativeConnection(connection), properties.getDatabase())) {
    writer.write(lines.toArray(new String[0]), SchemalessProtocolType.LINE,
            SchemalessTimestampType.MILLI_SECONDS, properties.getTtl(), 0L);
}
```

`nativeConnection`：原生 JNI 连接 `conn.unwrap(TSDBConnection.class)` 直用（writer 不关闭池连接）；REST 等非原生场景返回原连接由 writer 按元数据自建写入连接。写入异常抛 `IllegalStateException`，由数据服务侧的 try/catch 记日志降级。

### 6.4 查询（executeQuery）

JDBC 执行 SQL → ResultSet 映射为行 Map；列名/tag 名经 `TimeseriesLayout#rowKey` 归一化（下划线小写，与解码约定一致；TDengine 标识符大小写不敏感、JDBC 返回一律小写）。**表/列不存在**（产品尚无数据、属性从未上报）→ 返回空列表而非报错（错误信息含 `not exist` 判定），策略层无需判表存在。

## 7. 监听器（sa-admin `device.storage.listener`）

### 7.1 三个监听器与公共骨架

三个监听器均为 `@Component`、继承公共骨架 `CommonStorageListener`（`ignoreStorage` 判定、`resolveStoreContext` 设备上下文解析、`deviceName` 设备名解析、`StoreContext` 产品+设备名），用 Spring `@EventListener` 声明监听方法（`SpringEventBus.publish` 已把事件转发给 Spring 广播器，上行/下行发布点无需改动；`publishAsync` 在异步线程执行，监听方法天然异步、不阻塞消息处理链路）。

**监听器职责**：忽略标记跳过 → 设备上下文解析（设备不存在/未绑定产品 → 告警跳过）→ 消息 → 业务模型完整转换（含 productId/deviceName 回填，事件另取物模型回填 type/dataType）→ 调数据服务 `store(data)` 纯路由落库。**任何异常仅记日志，绝不阻断消息流**（try/catch 包住整段）。

| 监听器 | @EventListener 方法 | 转换要点 |
|---|---|---|
| `ReportPropertyStorageListener` | ① `onReportProperty(ReportPropertyMessage)`<br>② `onChildDeviceMessage(ChildDeviceMessage<ReportPropertyMessage>)` 泛型精准匹配，解包 `getChildDeviceMessage()` 后走同一 handle | productId/deviceName 取设备上下文回填；properties 原样 |
| `EventStorageListener` | ① `onEventMessage(EventMessage)`<br>② `onChildDeviceMessage(ChildDeviceMessage<EventMessage>)` 同构 | 设备上下文回填 productId/deviceName；另 `product.getMetadata().block()` 取物模型 —— `getEventOrNull(event)` 未定义 → 告警跳过不落库；`type` 取 `EventMetadata.getType()`、`dataType` 取 `valueType.getType()`，`data` 为消息 JSON |
| `MessageLogStorageListener` | `onDeviceMessage(AbstractDeviceMessage)` 单个方法覆盖全部设备消息（全部消息类型与子设备包装均继承 AbstractDeviceMessage） | `dispatchMessageLog` 类型判定 + 子设备解包取内层后，按内层消息转换全字段（deviceId/messageId/timestamp/content） |

**子设备消息（网关代理）解包后按内层消息处理**：`ChildDeviceMessage`/`ChildDeviceMessageReply` 递归解包至内层，`deviceId`/`messageId`/`timestamp`/`headers`（含 ignoreStorage 标记）均取内层（外层是网关三元与网关连接信息，日志归属应为子设备）。

### 7.2 消息日志类型判定（TopicMessageCodec 词汇表）

`dispatchMessageLog` 经 `TopicMessageCodec.fromMessage(message)` 统一判定（无法匹配 codec → null 跳过）：

- **direction** = codec 的 upstream 标记（true → `up` 设备上报/回复；false → `down` 平台下发）
- **commandType** = codec 枚举名，与存储 command_type、`DeviceLogTypeEnum`（后端查询枚举）、前端枚举**同源**，查询多选直传、前端按值渲染，全程无映射转换

| commandType | 方向 | 说明 |
|---|---|---|
| `register` / `unregister` / `online` / `offline` | up | 注册 / 注销 / 上线 / 离线 |
| `disconnect` | down | 平台断开连接下发 |
| `disconnectReply` | up | 断开连接回复 |
| `reportProperty` | up | 属性上报 |
| `readProperty` / `readPropertyReply` | down / up | 读取属性（下发 / 回复） |
| `writeProperty` / `writePropertyReply` | down / up | 设置属性（下发 / 回复） |
| `functionInvoke` / `functionInvokeReply` | down / up | 命令（下发 / 回复） |
| `event` | up | 事件上报 |

**全部消息类型均落库**（连接生命周期消息同样入库，供设备日志展示完整轨迹）；回复为名称带 `Reply` 后缀的上行消息，与命令**成对相邻**、互为独立类型（前端下拉多选，回复类型需单独勾选）。

**content** 为整条消息 Jackson 序列化（**全量含 headers，不清空**；回复的执行结果 success/code/message 含在回复消息 JSON 内，不单独落列）。

## 8. 数据服务（sa-admin `device.storage.service`）

三个数据服务均 `@Service`，注入 `DeviceRegistry`，经设备操作对象解析存储策略（`DeviceOperator.getStorageStrategy()` 恒非空，无需判空）。**`store(data)` 为纯路由落库入口**：转换（含上下文回填）已在监听器完成，服务内按策略 `save` 并在 try/catch 中记日志降级（**绝不阻断消息流**）；查询为同步读（内部 `.block()`，设备/产品缺失抛 `BusinessException`），存储未开启/无匹配策略时经空策略明确抛错（不静默返回空结果）。

| 服务 | `store`（落库入口） | 查询（同步读） |
|---|---|---|
| `DevicePropertyDataService` | `store(PropertyData)` → `requireStorageStrategy(deviceId).save(data)` | `queryLatestPropertyValues(deviceId, propertyIds)`：构造 `LatestPropertyQuery`（productId 经 resolveProduct 解析）交策略执行 —— 每属性独立取最后一条非空上报记录，返回 `Map<属性id, LatestPropertyValue>`（值 + 上报时间毫秒，策略按自身行形态取数；从未上报不含该键） |
| `DeviceEventDataService` | `store(EventData)` 同构 | `queryEvent(deviceId, event, startTime, endTime, pageNum, pageSize)`：`EventHistoryQuery` 交策略执行，策略内 count + 数据两查一次返回 `PageResult<EventData>` |
| `MessageLogDataService` | `store(MessageLogData)` 同构 | `queryLog(deviceId, commandTypes, direction, deviceName, startTime, endTime, pageNum, pageSize)`：`CommandLogQuery` 交策略执行；commandTypes 为日志类型多选集合（command_type tag IN，回复类型为独立类型随选随传）；direction/deviceName 可空；deviceName 为冗余字段**精确匹配** |

**解析链**（三个服务各自私有方法，不抽基类防过度设计）：

- 写路径 `requireStorageStrategy(deviceId)`：`registry.getDevice(deviceId).flatMap(DeviceOperator::getStorageStrategy).block()` —— 设备未绑定产品同样兜底空策略，block 恒非 null（监听器已在事件总线异步线程调用，不阻塞消息流）
- 读路径 `resolveProduct(deviceId)`：`registry.getDevice(deviceId).flatMap(DeviceOperator::getProduct).switchIfEmpty(Mono.error(...)).block()`，空或产品不存在抛 `BusinessException("设备不存在或未绑定产品")`；再取策略构造业务条件对象（productId 由产品对象提供）交策略

### 8.1 既有业务接入

- **`DeviceService.getProperties(deviceId, properties)`**（原 TODO 空实现，已实现）：设备未绑定产品 → 明确报错；属性定义来自产品物模型（入参空 = 全部属性，按物模型顺序；物模型不存在的入参属性跳过）→ `DevicePropertyDataService.queryLatestPropertyValues` 批量取最近上报值 → 组装 `DevicePropertyVO`（propertyId/propertyName/formatValue/上报时间）；无记录属性保留行（值/时间为空，前端显示无数据）—— 最近上报值快照查询，**不向设备下发、不阻塞**
- **`DeviceLogService.queryPage`**（消息日志分页）：委托 `MessageLogDataService.queryLog`（设备必选，缺失明确报错 `"请先选择设备再查询设备日志"`）；查询表单 `typeList`（`List<String>` 多选，`@CheckEnum` 集合校验：重复值拒绝、非法值拒绝）**直传**存储 command_type（不选 = 全部类型，含回复类型与连接生命周期消息），结果行 commandType 原样透出，前端按同源枚举渲染，**无需任何映射转换**；行 → `DeviceLogVO` 解码（timestamp 取存储行时间、**固定 +08:00** 转 `LocalDateTime`，见下）；下行与回复两行同 messageId，按时间倒序呈现命令生命周期
- **时间口径统一固定 +08:00**：`SmartLocalDateUtil.toLocalDateTime(long)` / `toEpochMillis(LocalDateTime)` 以 `ZoneOffset.ofHours(8)` 换算（不随部署机器时区变化），设备日志查询时间范围与展示时间据此对齐消息时间戳口径

## 10. 下行消息发布点改造（sa-base）

`LocalDeviceMessageSender`：

1. 构造器注入 `IEventBus`（`EventBusAutoConfiguration` 已无条件装配该 bean）
2. `doSend` 发送成功后发布（**失败不发布**——命令未真正到达设备，不入库）：

```java
.flatMap(target::send)
.doOnSuccess(ignore -> eventBus.publishAsync(message))   // message = prepareMessage 填充后（含 messageId/deviceId/timestamp）
.then();
```

3. 发布对象为填充后的消息（子设备命令即 `ChildDeviceMessage` 外层，内层已含子设备 deviceId）；`sendAndWait`/`send` 共用 `doSend` 均覆盖；集群远端转发最终落在设备所在节点的 localSender，恰好发布一次
4. **回复不在此发布**——`DefaultDecodedClientMessageHandler` 已把全部上行消息（含回复）发布到总线，回复行由消息日志监听器经既有路径入库
5. `DeviceMessageSenderAutoConfiguration.localDeviceMessageSender` bean 方法追加 `IEventBus` 参数
6. **下行结果不回填 —— 时序库只追加、绝不 UPDATE**：TDengine 不支持修改历史行，下行行只记 direction/commandType/content；设备回复走上行路径落**独立一行**（direction=up、同 messageId），执行结果含在回复行的 content JSON 内，不单独落列。查询侧按 messageId 关联两行即可还原命令完整生命周期，全程零修改、纯追加写入

## 11. 配置与装配

### 11.1 StorageAutoConfiguration（sa-base `storage.config`）— 注册器恒装配（策略无关）

与具体库无关，只承担策略收集与兜底；将来新增 Influxdb 等策略**零改动**：

```java
@Configuration
public class StorageAutoConfiguration {

    /** 注册器 — 恒装配（无开关条件）；List 注入收集容器内全部 StorageStrategy 策略 bean，并内置 EmptyStorageStrategy 兜底 */
    @Bean
    public StorageStrategyRegistry storageStrategyRegistry(List<StorageStrategy> strategyList) { ... }
}
```

**总开关不在此声明**：`iot.storage.enabled=false`（默认）时策略 bean（tdengine 等，自带装配条件见 §11.2）不装配，`strategyList` 为空列表（Spring 注入空列表而非 null）→ 注册表为空但注册器与 EmptyStorageStrategy 仍存在，`get()` 返回空策略：写入告警一次不阻断消息流、查询明确抛错（详见 §3.3）—— 无 TDengine 环境应用照常启动。

### 11.2 TdengineAutoConfiguration（sa-base `storage.tdengine`）— TDengine 策略专属

```java
@Configuration
@EnableConfigurationProperties(TdengineProperties.class)
@ConditionalOnProperty(prefix = "iot.storage", name = "enabled", havingValue = "true")
public class TdengineAutoConfiguration {

    // @ConditionalOnProperty 不可重复，tdengine.enabled（默认开）作为第二条件注解在 tdengine 专属 bean 上

    /** TDengine 独立数据源 — url 不带库名（库由通道建库后按 dbName 写入）；惰性建连，非 @Primary */
    @Bean(name = "tdengineDataSource", initMethod = "init", destroyMethod = "close")
    @ConditionalOnProperty(prefix = "iot.storage.tdengine", name = "enabled", havingValue = "true", matchIfMissing = true)
    public DruidDataSource tdengineDataSource(TdengineProperties properties) { ... }

    /** TDengine 物理读写通道 — 行/单值列两策略共享（建库 @PostConstruct 仅执行一次） */
    @Bean
    public TdengineChannel tdengineChannel(...) { ... }

    /** TDengine 行布局策略（tdengine-row） */
    @Bean
    public TdengineRowStrategy tdengineRowStrategy(@Qualifier("tdengineChannel") TimeseriesChannel channel) { ... }

    /** TDengine 单值列布局策略（tdengine-column） */
    @Bean
    public TdengineColumnStrategy tdengineColumnStrategy(@Qualifier("tdengineChannel") TimeseriesChannel channel) { ... }
}
```

**注意**：Spring Boot 2.7 的 `@ConditionalOnProperty` **不可重复**（重复注解为编译期错误）—— 总开关（`iot.storage.enabled`）放类级，策略开关（`iot.storage.tdengine.enabled`，matchIfMissing 默认开）放 tdengine 专属 bean 方法级；`TdengineProperties` 经 `@EnableConfigurationProperties` 注册（类上不再手写 @Bean 方法）。将来 influxdb 等新时序库按同构新增 AutoConfiguration（通道 + 策略叶子），通用装配零改动。
